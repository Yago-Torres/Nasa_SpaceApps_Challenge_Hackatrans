# Case report and verifiable export (ABB-26)

Status: **IMPLEMENTED & TESTED** (API + web). Preliminary technical record; never a diagnosis.

## What is stored

`POST /api/v1/cases/{case_id}/reports` (OWNER, EDITOR or REVIEWER) reads the case **as it is stored at that moment**, builds a JSON
snapshot and renders it twice (Markdown, HTML). One row of `reports` keeps all three plus:

| Field | Meaning |
|---|---|
| `version` | 1, 2, 3 … per case (never reused). |
| `generated_at`, `generated_by_id`, `case_version` | When, by whom (display name is shown only inside the app, never in the document) and which case version it came from. |
| `checksum_sha256` | SHA-256 of the Markdown text. `html_sha256` and `snapshot_sha256` (canonical JSON) cover the other two representations. |
| `sources_sha256`, `source_manifest_ids` | One hash over `id:retrieval-checksum:content-checksum` of every source manifest used, plus the IDs. |
| `changes` | Records added / removed / changed since the previous stored version, by ID. |

Migration `d5f3a8b21c64` adds a database trigger: after insert, the content columns can no longer be updated (even by the API user).
`GET …/reports/{version}/verify` recomputes every hash and re-renders the Markdown from the stored snapshot; it reports `valid: false`
if anything differs (this is how tampering by a database administrator would show).

## What the document contains

Version/date/case-version/hashes; changes since the previous version; context (incident period, crop history as reported, parcels
as "Parcel N" with the owner's region label only); every **source manifest** (provider, dataset, endpoint without query, retrieval
instant, dataset and processing version, retrieval and content checksums, event year and reference window, resolutions, licence,
limitations; superseded revisions are listed as such); **monthly observed values and anomalies** of the current revisions with
reference mean, number of reference years, descriptive departure class and quality flags; **hypotheses** with status, evaluation note,
missing evidence and limitations; **literature claims** with class (`LITERATURE_REVIEWED` only when ACCEPTED, otherwise
`LITERATURE_METADATA`), DOI (linked only if it is a syntactically valid DOI), study design, evidence basis and claim ID;
**human-authored conclusions** with review status; **rotation strategies** (current + rule-generated alternatives from the
deterministic ABB-17 engine, with conflicts, risks, unverified benefits, metadata-only references, rule-set/catalogue versions and the
SHA-256 of the farm profile used); counts of collaboration (members per role, comments, reviewed claims/conclusions); privacy
statement; limitations.

Nothing is invented: an empty section says so ("No hypothesis is recorded…"). Rotations appear only when a farm profile is supplied to
the API (`{"rotation": {"profile": …}}`); the server runs the comparison itself and never accepts client-computed rotations. The web
tab currently generates reports **without** a profile because the app does not yet persist the farm profile per case; the section then
states that no rotation comparison is included.

## Privacy of exports

Never included, for any role: exact coordinates, the generalised grid-cell centre, free-text incident notes, e-mail addresses, member
display names, comment text, parcel labels. Source endpoints lose their query string; only `start`, `end`, `community`, `parameters`,
`format`, `time-standard` request parameters are kept. A final guard replaces any stored coordinate value that still appears in any
text with `[location withheld]` and states the count. Markdown and HTML are neutralised (`|`, `<`, `>`, HTML escaping, CSP `default-src 'none'`,
`sandbox`); download responses are `no-store`, `nosniff`.

## Formats

Markdown (`text/markdown`), HTML (print styles; use "Save as PDF" in the browser) and the JSON snapshot. **PDF is not generated by the
server**: it needs a rendering dependency (not added without an ADR). Each download returns `X-Report-SHA256`.

## Tests (real results)

`backend/tests/test_case_report_offline.py` (8 tests, no database) and `test_case_report_api.py` (6 tests, PostgreSQL via
`TEST_DATABASE_URL`, NASA POWER simulated with the ABB-10 MockTransport series, synthetic people/parcels/DOIs): migration down/up, write-once
trigger, a case combining ingested NASA data + an accepted and a pending claim + hypothesis + reviewed conclusion + collaboration +
4 rotation strategies, no leakage of coordinates/notes/e-mails/names/comments in Markdown, HTML or JSON, regenerated versions listing
ADDED/CHANGED records, byte-identical older versions, role checks (viewer 403 on generate, stranger 404), tamper detection, coordinate guard.
Web: `frontend/src/features/cases/report/CaseReport.test.tsx` (6 tests, fetch mocked).

## Limitations / open

- No PDF; no digital signature (hashes prove integrity of what is stored, not who vouches for it).
- Report `status` stays `PRELIMINARY`; no `REVIEWED` workflow yet (needs ABB-25 review of a report target).
- Observed values come only from NASA POWER manifests stored for the case (GPM/HLS not built).
- Rotations in the web tab pending persisted farm profile; stored `rotations` rows (none are written by any API yet) are listed if present.
- Not yet run against a real NASA POWER retrieval in CI (simulated payload); scientific review of wording still required.
